# Desktop Unity recovery: practical workflow

## Read-only inventory

- Windows distribution: inspect `<Game>.exe`, `UnityPlayer.dll` file version, `GameAssembly.dll`, `<Game>_Data/globalgamemanagers`, `level*`, `sharedassets*.assets`, streamed `.resS`, `StreamingAssets`, bundles and platform plugin directories. UnityPlayer's version is a useful hint; verify against the game data/tool output. Cross-check the binary and metadata from the same version and architecture.
- Enumerate file types, scene candidates, audio banks and compressed resources. Large filenames or byte counts are inventory, not an estimate of recoverability. Avoid executing user-supplied binaries or launchers for a static inspection. Record exact version and hash of reference builds and compare same versions; a screenshot version label may differ from the analyzed build.
- Ask the tools themselves for supported versions/flags. `Cpp2IL --list-output-formats` identifies available IDs; e.g. `diffable-cs` and `dummydll` may be available, but generated structure does not recover native method bodies. REA's IL2CPP inspection likewise produces metadata and optional binary-linkage evidence, not a Unity project or gameplay implementation.

## Export and asset accounting

1. Verify the AssetRipper server UI/address and whether an existing session is in use. Load the complete game folder and export into an absent output directory, then confirm actual completion and inspect its `ExportedProject/Assets`, `Packages`, `ProjectSettings`, logs and error counts. A successful HTTP response alone is not a complete-quality check. Never issue `Reset` on a shared service without establishing ownership.
2. Keep source, raw export and working copy distinct. Preserve each `.meta` and all original assets; choose names and directories to match the user's project conventions. Do not put the validation build inside `Assets`.
3. Count and sample scenes, prefabs, textures, meshes, animation, terrain, materials, audio and localization. Keep original bank files: an FMOD bank existing on disk does not prove events, sound mappings or playback were recovered. Addressables bundles and metadata can need separate inspection. A UnityPy extraction failure may be an empty placeholder or a real missing resource; inspect representative data before deciding.
4. Test a validation copy with the closest available compatible Editor before moving dependencies to the working project. Record the original and editor versions and the exact failure. Shipped/auto-generated assemblies may be dummy metadata, incompatible native plugins or duplicates of built-in packages. Diagnose by assembly identity and plugin import settings; do not install every exported DLL blindly or silence compile errors by deleting evidence.

## Script references and game logic

- Group missing-script references by `(GUID, fileID)` and identify the owning assembly using the export's `.meta` files. Verify package, namespace and class identity before mapping to installed Unity UI, TMP, Localization, Cinemachine, Input System or other package scripts. Script fileID algorithms and GUID mappings depend on assembly/type/version; validate known cases on a small copy and use Unity APIs/MCP for serialized edits.
- Preserve the original serialized data and backups. Do not manually patch live `.unity`, `.prefab` or `.asset` YAML while Unity is open. Match existing project instructions and use supported editor operations. Save and read back changed assets, and rescan missing references.
- A stub assembly may restore component identities and serialized fields without implementing any methods. Inventory gameplay obligations independently: input, scene transitions, spawn, enemy AI, weapons, UI, objectives, upgrades, win/loss, saves and audio. Use native analysis or controlled observed behavior as evidence for each; label reconstructed logic separately.

## Rendering and UI

- A white or pink scene can have several causes: wrong pipeline or quality override, generated shader placeholder, missing texture, unsupported VFX, lighting/camera/postprocessing, or an inactive object. Inspect scene hierarchy and representative materials through the editor first, including the **asset path** of the shader and the actual texture property (for example `_BaseMap` versus `_MainTex`). Same-named exported and official shaders can be different assets.
- `//DummyShaderTextExporter` or an unconditional white fragment demonstrates an export placeholder, not the original Shader Graph. Preserve the original shader and material data. For a standard URP material, test the verified matching official package shader on a backed-up representative material; read back its texture bindings and compare a screenshot. For custom ground/foliage/fire shaders, reconstruct from available properties, textures and visual evidence; disclose simplifications such as omitted wind, lighting, shadows or graph logic. Replacing a shader with a broadly similar one is not proof of fidelity.
- Package installation and resolution are asynchronous. Check requested, locked and loaded version separately; do not repeat an ambiguous mutation after a timeout. Record the original manifest/settings and check all quality levels. Unity may reimport thousands of assets and temporarily stop servicing MCP. Wait and inspect editor state/logs; don't claim success solely because the dependency was added to the manifest.
- VFX Graph warnings from compiled exported assets may require original graphs or a deliberate reconstruction; installing a package alone does not prove recovery. Categorize warnings and errors with baseline evidence; fix their causes where justified, and disclose unresolved items instead of clearing or hiding them.

## Runtime validation

- Connect to the existing Unity MCP and verify project path, current scene, dirty state, mode and compilation. Follow the provider's documented task/readback protocol for mode changes; after a timeout, inspect status before retrying. Do not install or replace a bridge without authorization.
- Before a screenshot comparison, match game version, scene, camera, locale, aspect ratio and state. Record exact target and expected interaction. In Play Mode, inject actual inputs over appropriate frames and observe scene, UI or game state; a tool's `dispatched`/`success` result only proves delivery was attempted. Record the failure if a missing component or unavailable input stops the flow.
- Exit Play after testing unless the user requests otherwise; avoid saving runtime state. Capture Console baseline, compilation status, scene and prefab references, input results, screenshots and unresolved differences. Test target-specific builds and real devices separately. Do not present editor screenshots, a successful export or a dummy-DLL compile as a complete restoration.
